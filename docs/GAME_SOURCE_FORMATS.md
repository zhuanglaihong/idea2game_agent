# 游戏视角、源码工程与能力边界

## 2D、2.5D 和 3D

当前 Demo 的武侠大乱斗默认使用 2.5D：二维世界坐标计算碰撞，斜视投影绘制菱形地面、平台厚度和立绘，按屏幕深度排序角色与飞刀。触摸坐标使用反向投影，因此点击位置与实际移动位置一致。这不是完整的三维模型或自由旋转相机。

输入「改成2D俯视版本」保留原玩法切换视角；「改成2.5D斜视版本」切回。视角参数保存在作品和分享链接中，源码导出也保留。修改视角会重新加载当前游戏，不保留正在进行的战斗。旧的2D绘制代码没有删除。

正式平台的提示词路由已经为复杂3D、Three.js、游戏引擎和多场景游戏预留 VUE_PROJECT 生成方式，简单2.5D可使用Canvas。提示词具备要求不代表运行质量已经得到验证；复杂游戏仍需实际构建、试玩与修复。

## 下载源码下拉框

游戏行业不存在一种通用源码格式；ZIP只是打包容器，必须区分语言、引擎、工程和构建产物。当前实现：

| 选项 | 实际交付 | 支持状态 |
| --- | --- | --- |
| Web JavaScript工程 | index.html、src/game/runtime.js、assets、参数清单、README | 可下载，可直接打开或静态部署 |
| Web TypeScript/Vite工程 | TS入口与配置类型、JS游戏运行时、package.json、tsconfig、Vite配置、public素材 | 可下载，已验证类型检查和生产构建 |
| 单文件HTML | 内嵌JS与图片的便携源码 | 可下载，适合快速离线试玩 |
| Godot/GDScript工程 | 需要project.godot、场景、脚本与Godot构建 | 尚未适配，选项禁用 |
| Unity/C#工程 | 需要Assets、ProjectSettings、Packages与Unity构建 | 尚未适配，选项禁用 |

TypeScript工程保留现有JavaScript运行时，不声称游戏逻辑已全部迁移并进行严格类型检查。可直接维护运行时，也可逐步迁移为TS。Web工程没有改写成Phaser、Unity或Godot引擎。不能把现有JS换扩展名当成C#或GDScript源码。

浏览器引擎也可使用JavaScript或TypeScript，例如[Phaser的官方工程模板](https://docs.phaser.io/phaser/getting-started/project-templates)。Godot与Unity可产生网页构建，但需要各自工具链和目标平台适配，最终网页入口仍可以是HTML；参见[Godot网页导出说明](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)。

下一阶段应在生成前选择目标引擎，把玩法需求和素材清单交给对应生成器；构建服务分别验证npm、Godot或Unity工程，再输出源码包和可发布的网页构建。统一的是需求、素材、作品与发布流程，不是任意源码自动无损互转。

## 参考射击游戏是否能实现

[参考站点 StarCraft: Ashfall](https://starcraft-shooter-2026.pages.dev/)页面显示自动射击、左右增援路线、多个兵种、经验成长、关卡任务、画质和声音设置。仅凭这些可见界面不能确认作者使用的引擎，也不能证明其代码与本平台兼容。

同类原创浏览器游戏的可玩原型在当前架构的技术范围内：现有LLM代码生成、多文件/Vue工程保存、npm构建、预览与静态发布提供基础。已有Demo也验证了自动射击、敌潮、升级、关卡与2.5D投影。但当前公开Demo仍是预录回放和参数模板，尚未连接公网AI后端，不能自动生成该站点同等完成度的作品。

达到接近的完整体验还需：稳定的Canvas/Phaser或Three.js运行时、成套角色动画或3D资产与音效、兵种/关卡数据、粒子及伤害反馈、移动端性能和输入适配，以及构建试玩修复流程。高质量图片生成解决部分美术需求，不会自动提供可用骨骼动画、3D模型、游戏逻辑或性能优化。

## 本次验证

游戏规则测试覆盖飞刀碰撞、经验拾取、升级、重开与关卡推进；新增投影/反投影一致性及视角数据校验。导出测试检查JS/TS目录、入口、图片、配置和构建脚本；导出的Vite工程已通过tsc与vite build。公开网站源码包不包含平台后端和模型密钥。
